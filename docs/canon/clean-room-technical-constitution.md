# Clean-room Technical Constitution v1 (Draft)

## Status

Draft — Technical Governance Layer  
Clean-room rebuild foundation document.

This document defines:

- technical governance principles,
- architectural boundaries,
- clean-room implementation constraints,
- runtime separation rules,
- documentation authority rules,
- and forbidden technical patterns.

This is not:
- an implementation roadmap,
- a schema specification,
- a framework selection document,
- or a deployment strategy.

The purpose of this document is:
# preserving Lumira’s reflective philosophy during implementation.

---

# 1. Core Technical Principle

The technical architecture exists to preserve reflective integrity.

Implementation decisions must optimize for:
- clarity,
- restraint,
- continuity integrity,
- emotional safety,
- and architectural legibility.

Not:
- feature density,
- engagement maximization,
- or architectural cleverness.

---

# 2. Canonical Authority Hierarchy

The clean-room rebuild must follow this authority order:

```txt
Constitution
    ↓
Minimal Reflective Runtime
    ↓
Technical Constitution
    ↓
Runtime Architecture
    ↓
Schema / APIs / UI
````

If lower layers conflict with higher layers:

* higher layers always win.

---

# 3. Documentation Authority Rules

Primary build authority:

```txt
docs/canon/
```

Secondary authority:

```txt
docs/runtime/
```

Historical-only reference:

```txt
docs/archive/legacy-transition/
```

Legacy compatibility documents must never override:

* canonical runtime philosophy,
* reflective constraints,
* or clean-room ontology.

---

# 4. Reflective Space Primacy

The primary runtime ontology is:

# Reflective Space

Not:

* sessions,
* routes,
* flows,
* dashboards,
* or workflows.

Technical systems must model:

* continuity,
* reflective movement,
* and symbolic context.

Not rigid progression containers.

---

# 5. Dreams Are Reflective Anchors

Dream entries are:

* primary experiential anchors,
* not isolated workflow sessions.

The runtime must support:

* cross-dream continuity,
* multi-dream threads,
* revisitation,
* lateral movement,
* and evolving symbolic association.

No architectural decision should permanently trap reflective continuity inside a single dream container.

---

# 6. Internal vs External Cognition Separation

The system must maintain strict separation between:

## Internal reflective cognition

and

## User-facing reflective communication

Internal cognition may:

* infer,
* model,
* connect,
* estimate,
* and prioritize.

User-facing systems must remain:

* uncertainty-aware,
* optional,
* non-authoritative,
* and emotionally restrained.

Internal cognition is never surfaced directly as truth.

---

# 7. Observation Layer Rules

Observation is descriptive.

Observation systems may:

* structure,
* categorize,
* organize,
* and contextualize dream material.

Observation systems must not:

* collapse ambiguity,
* generate interpretive certainty,
* or behave like symbolic decoding engines.

Observation should remain:

* evidence-linked,
* phenomenological,
* and revisable.

---

# 8. Latent Layer Rules

Latent cognition is:

# runtime cognition infrastructure.

Not:

* UI content,
* insight feed,
* or authority engine.

Latent systems may:

* support orientation,
* shape openings,
* identify recurrence,
* detect continuity,
* and estimate reflective salience.

Latent outputs must remain:

* probabilistic,
* bounded,
* uncertainty-aware,
* and reversible.

No latent system may produce:

* deterministic psychological claims,
* symbolic certainty,
* or hidden authority escalation.

---

# 9. Reflective Thread Rules

Threads are:

# continuity trajectories.

Not:

* tasks,
* completion systems,
* or workflow stages.

Thread systems must support:

* dormancy,
* reactivation,
* branching,
* contextual movement,
* and unresolvedness.

Thread systems must never:

* pressure completion,
* enforce closure,
* or simulate productivity mechanics.

---

# 10. Glossary Rules

Glossary systems are:

# autobiographical symbolic memory.

Not:

* universal symbolic truth systems.

Glossary systems may:

* preserve recurrence,
* store user-associated meaning,
* and support continuity orientation.

Glossary systems must never:

* override current experience,
* enforce symbolic consistency,
* or generate universal symbolic interpretation.

---

# 11. Openings and Invitations

Openings are:

# reflective invitations.

Not:

* tasks,
* prompts-for-engagement,
* or progression requirements.

Opening systems must optimize for:

* resonance,
* calmness,
* emotional legibility,
* and restraint.

The runtime must preserve:

# silence legitimacy.

The AI must know when not to ask.

---

# 12. Runtime Pacing Rules

All runtime layers must preserve:

* emotional spaciousness,
* cognitive breathability,
* and reflective calmness.

The runtime must avoid:

* continuity flooding,
* dense resurfacing,
* excessive association chains,
* interpretive overload,
* and compulsive reflective loops.

When uncertainty rises:

* omission is preferred over forced surfacing.

---

# 13. Forbidden Technical Patterns

The clean-room rebuild must avoid:

* workflow-first architecture
* route-owned cognition
* hidden progression systems
* engagement optimization loops
* streak mechanics
* completion pressure
* “continue unfinished work” framing
* mandatory reflective flows
* authority-language generation
* hidden emotional ranking systems
* dense notification systems
* AI intimacy simulation
* symbolic scoring engines
* infinite reflective feeds
* compulsive resurfacing logic
* forced continuity generation
* synthetic narrative compression
* over-connected graph hallucination

---

# 14. Simplicity Over Intelligence

A smaller but coherent runtime is preferable to:

* a highly intelligent but psychologically unstable system.

Technical systems should prioritize:

* understandability,
* composability,
* observability,
* and restraint.

Avoid:

* premature complexity,
* over-generalized orchestration,
* and speculative architecture.

---

# 15. Runtime Transparency

The runtime should remain:

* structurally understandable,
* inspectable,
* and conceptually legible.

The system should avoid:

* opaque behavioral emergence,
* hidden orchestration layers,
* and undocumented cognition mutation.

Important reflective behavior should remain explainable at architectural level.

---

# 16. Domain Separation

The rebuild should separate:

## Experiential layer

Dreams, scenes, highlights, reflections

## Observation layer

Descriptive orientation structures

## Latent cognition layer

Internal reflective reasoning

## Continuity layer

Threads, recurrence, symbolic memory

## Interaction layer

Openings, navigation, reflective movement

No single layer should collapse all responsibilities into itself.

---

# 17. User Ownership Rules

The runtime must preserve:

# user meaning ownership.

No system may:

* imply psychological superiority,
* present inferred meaning as truth,
* or pressure user agreement.

User-facing language must remain:

* invitational,
* revisable,
* and uncertainty-aware.

---

# 18. UI Architecture Philosophy

UI should emerge from:

* reflective pacing,
* continuity orientation,
* and emotional spaciousness.

Not:

* dashboard density,
* productivity ergonomics,
* or engagement maximization.

The UI should feel:

* calm,
* breathable,
* phenomenological,
* and continuity-sensitive.

---

# 19. Clean-room Rebuild Philosophy

The rebuild is not:

# a migration.

It is:

# a re-foundation.

Legacy systems should be treated as:

* reference material,
* not architectural destiny.

Only:

* proven reflective invariants,
* canonical philosophy,
* and stable continuity concepts
  should survive into the clean-room runtime.

---

# 20. Final Technical Principle

The architecture should preserve the feeling that:

# the user is moving through a living reflective space,

not:

* operating a productivity machine,
* optimizing a self-improvement loop,
* or consuming AI-generated meaning.

Every technical decision should be evaluated against this principle.
