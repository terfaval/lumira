# Lumira Reflective Space IA v0

## Purpose

This document defines the conceptual information architecture of Lumira’s Reflective Space.

It describes:

* how Reflective Space is structured,
* how reflective layers and states behave,
* how users move through reflective attention,
* where highlights, glossary motifs, and threads appear,
* how reflective writing emerges,
* and how the system avoids collapsing into workflow, dashboard, or chatbot UX patterns.

This document is:

* interaction-focused,
* UX-oriented,
* implementation-agnostic.

It is NOT:

* a visual component specification,
* a design system,
* or an implementation plan.

---

# 1. Core IA philosophy

Reflective Space is:

# one dream-centered workspace.

Not:

* a collection of disconnected pages,
* a wizard sequence,
* or a route-driven workflow.

Technical routes may remain temporarily.

But experientially:

* Frame
* Direction
* Work
* Summary
* Highlights

should increasingly behave as:

# layers and states of the same reflective environment.

---

# 2. Core experiential model

Reflective Space supports two major reflective modes:

| Mode                  | Primary activity                       |
| --------------------- | -------------------------------------- |
| Orientation Layer     | perceive / orient / recognize openings |
| Deep Reflection Layer | respond / deepen / continue            |

These are:

* attention states,
* not rigid application modes.

The transition between them should feel:

* gradual,
* contextual,
* and reflective.

Not:

* abrupt,
* workflow-like,
* or tool-switching.

---

# 3. Default Reflective Space view

Default Reflective Space should open into:

# Dream Surface + Orientation Layer.

The initial state prioritizes:

* re-entry into the dream,
* reflective orientation,
* and awareness of active reflective structures.

The user should quickly understand:

* where reflective gravity currently exists,
* what is unresolved,
* what has already deepened,
* and what remains available.

---

# 4. Dream Surface behavior

The Dream Surface is:

# the central substrate of Reflective Space.

It contains:

* raw dream text,
* highlights,
* motif markers,
* continuity anchors,
* reflective references,
* and contextual thread links.

---

## Dream Surface rules

The Dream Surface:

* remains canonical,
* remains accessible,
* and remains visually primary.

AI-generated orientation content:

* may help contextualize,
* but never replaces the dream itself.

---

## Dream Surface interaction model

Users may:

* highlight,
* attach notes,
* open threads,
* revisit prior reflections,
* connect motifs,
* or enter deeper reflection.

Interaction should feel:

* fluid,
* low-pressure,
* and continuity-aware.

---

# 5. Orientation Layer

## Purpose

Orientation Layer acts as:

# reflective topology surface.

Not:

* dashboard,
* analytics view,
* or AI report.

---

## Orientation Layer contents

May include:

* reflective openings
* unresolved areas
* active threads
* revisited motifs
* glossary continuity
* reflective density signals
* latent ambiguity candidates
* continuity cues
* dormant-but-relevant structures

---

## Important behavioral rule

Orientation Layer should behave as:

# collaborative reflective negotiation space.

Meaning:
the system surfaces structures that may require:

* confirmation,
* clarification,
* rejection,
* expansion,
* or personal context.

Examples:

* possible motif recurrence
* uncertain emotional continuity
* unresolved relationship dynamic
* latent symbolic cluster
* glossary promotion candidate

The user participates in:

# shaping reflective topology.

---

# 6. Orientation Layer density philosophy

Orientation Layer should remain:

* calm,
* sparse,
* and selectively surfaced.

Not every:

* motif,
* unresolved thread,
* continuity signal,
* or reflective opening
  should become foreground simultaneously.

The system continuously distinguishes between:

* foreground reflective structures
* background reflective structures

---

## Foreground reflective structures

Examples:

* currently active
* emotionally dense
* revisited
* unresolved
* user-confirmed
* continuity-active

These receive:

* stronger visibility
* greater interaction affordance
* reflective emphasis

---

## Background reflective structures

Examples:

* historical
* dormant
* lightly connected
* low-priority continuity
* weakly unresolved

These remain:

* ambient
* quiet
* peripheral
* resurfacable

---

# 7. Deep Reflection Layer

## Purpose

Deep Reflection Layer narrows reflective attention around:

# one active reflective center.

Examples:

* a thread
* a motif
* a highlight cluster
* an unresolved tension
* a reflective opening
* a continuity trajectory

---

## Deep Reflection behavior

Deep Reflection should:

* reduce reflective saturation,
* suppress peripheral noise,
* expand reflective writing space,
* and preserve nearby continuity context.

The user should feel:

# “stay with this.”

---

## Important rule

Deep Reflection must NOT become:

* empty writing mode,
* isolated editor,
* or pure fullscreen text area.

Relevant context should remain lightly accessible:

* dream excerpts
* nearby highlights
* related thread history
* reflective openings
* connected motifs

But:

# one reflective center dominates.

---

# 8. Entry threshold into Deep Reflection

Transition into Deep Reflection may occur through:

* longer reflective writing,
* opening a thread,
* expanding a reflective opening,
* revisiting unresolved material,
* or explicit focus action.

Short interactions:

* highlight notes
* quick associations
* motif tags

may remain inside Orientation Layer context.

The transition should feel:

* natural,
* not modal.

---

# 9. Inline Composer placement

Inline Composer appears:

* attached to local reflective objects.

Examples:

* highlight
* motif
* glossary occurrence
* thread node
* dream excerpt

---

## Inline Composer purpose

Supports:

* quick notes
* associations
* emotional marking
* local context
* lightweight continuity

---

## Behavioral rules

Inline Composer:

* expands gently
* remains contextual
* collapses naturally
* does not interrupt reflective flow

---

# 10. Reflective Composer placement

Reflective Composer belongs primarily to:

# Deep Reflection Layer.

It is attached to:

* current reflective focus,
  not:
* isolated UI objects.

---

## Reflective Composer behavior

Supports:

* sustained reflection
* thread continuation
* unresolved exploration
* continuity-building writing
* reflective deepening

---

## Important rule

Reflective Composer is NOT:

* chatbot input
* note app textarea
* form field
* comment box

It behaves as:

# active reflective field.

---

# 11. Reflective openings placement

Reflective openings may appear:

* near highlights
* inside active thread context
* inside Orientation Layer
* during revisitation
* after reflective responses

They should behave as:

# ambient reflective invitations.

Never:

# mandatory progression prompts.

---

# 12. Highlights expansion model

Highlights act as:

# reflective anchors.

Selecting a highlight may reveal:

* attached notes
* glossary links
* continuity signals
* related dreams
* reflective openings
* thread links
* revisitation history

---

## Highlight expansion behavior

Expansion should feel:

* contextual
* layered
* non-disruptive

Not:

* like opening separate applications.

---

# 13. Glossary motif expansion

Glossary motifs appear:

* contextually,
* not as dominant panels.

Motif expansion may reveal:

* recurrence
* personal notes
* related dreams
* reflective continuity
* connected highlights
* motif-linked threads

---

## Glossary philosophy

Glossary remains:

# personal motif memory.

Not:

* symbolic authority.

---

# 14. Thread list behavior

Threads are:

# reflective continuity structures.

Not:

* task queues,
* inboxes,
* or question histories.

---

## Thread visibility

Visible threads should prioritize:

* active continuity
* revisitation
* unresolved density
* user-confirmed importance

Not:

* chronological exhaustiveness.

---

## Thread navigation

Users navigate:

# through reflective continuity,

not:

# workflow progression.

Possible navigation:

* revisit prior reflective state
* branch sideways
* reconnect dormant thread
* deepen existing reflective center

---

# 15. Thread focus state

Opening a thread enters:

# focused reflective narrowing.

Thread focus may display:

* reflective center
* linked highlights
* related excerpts
* previous responses
* nearby continuity
* reflective openings
* reflective composer

The thread itself should feel:

# alive and revisitable.

Not:

# completed.

---

# 16. Mobile behavior

Mobile Reflective Space prioritizes:

* calm cognition
* thumb ergonomics
* reduced density
* and layered focus.

---

## Mobile default state

Default mobile state:

* Dream Surface
* lightweight Orientation Layer
* compact reflective indicators

Additional structures open through:

* sheets
* focus states
* contextual expansion

---

## Mobile Deep Reflection

During sustained reflection:

* surrounding chrome softens
* orientation density reduces
* reflective composer expands
* local continuity remains accessible

---

# 17. Archive and sidebar behavior

All dream entry points should eventually open:

# the same Reflective Space entry.

This includes:

* archive
* sidebar
* glossary links
* session lists
* related dream references

---

## Re-entry behavior

Re-entry should restore:

* reflective continuity,
* not application navigation state.

Examples:

* active thread
* revisited motif
* unresolved focus
* recent reflective center

---

# 18. Route-to-state migration philosophy

Current routes may remain:

* temporarily,
* for implementation compatibility.

Long-term experiential mappings:

| Legacy route | Reflective interpretation    |
| ------------ | ---------------------------- |
| Frame        | orientation surface          |
| Direction    | attention weighting          |
| Work         | reflective thread focus      |
| Summary      | reflective workspace default |
| Highlights   | reflective anchor layer      |

The system should increasingly feel:

# state-based rather than route-based.

---

# 19. Reflective pacing philosophy

Reflective Space should preserve:

# contemplative pacing.

The system should:

* avoid excessive prompting
* avoid simultaneous reflective demand
* avoid workflow urgency
* avoid gamified progression

The system should instead:

* surface selectively
* deepen gradually
* preserve quietness
* and allow dormant continuity.

---

# 20. Final principle

Reflective Space should not feel like:

* operating software.

It should feel like:

# remaining inside a living relationship with a dream over time.
